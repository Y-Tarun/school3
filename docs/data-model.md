# Data model

This document describes the PostgreSQL/Prisma schema and its versioned migrations.
Student records and
photograph references are sensitive; all student detail fields belong to immutable
revision snapshots. Only application number and first name are required for a student
revision. All other legacy student detail fields are nullable.

## Stable identity and immutable revisions

- `Student` is the stable identity and stores `currentApplicationNumber` (unique),
  lifecycle state, timestamps, and its required current-revision pointer.
- `StudentRevision` contains the full snapshot and acting admin. The pair
  `(studentId, revisionNumber)` is unique. Revisions link to their base revision using
  `(basedOnRevisionId, studentId)`, preventing cross-student lineage.
- `Student.currentRevisionId` and `currentApplicationNumber` are required and constrained to the
  same revision owned by that student using the composite foreign key
  `(currentRevisionId, id, currentApplicationNumber) -> (id, studentId, applicationNumber)`.
  The initial revision and student can be inserted in either order inside a transaction
  because the migration defers this circular foreign key until transaction commit.
  No committed student can lack a current revision or point at another student's
  revision.
- Foreign keys use restrictive deletion behavior. Normal workflows must not update or
  delete revisions or physically delete students.
- PostgreSQL check constraints reject negative non-null sibling counts.
- Application-number changes must update the current number and create a revision in a
  single transaction. PostgreSQL's unique constraint arbitrates concurrent conflicts.
- Student edits lock the stable student row while choosing the next revision number and
  updating the current pointer. An edit based on an older snapshot is still allowed;
  it produces a snapshot from that base plus the submitted changes and reports
  `staleBase: true`. It does not merge other concurrent edits.
- `lifecycleStatus` (`Active`/`Inactive`) is separate from admission `status`; making a
  student inactive does not change the admission status.

## Supporting models

- `Admin` stores a normalized unique email, Argon2id password hash, and the initial
  single role. There is no public admin registration.
- `RefreshToken` stores a unique token hash, session ID, expiry/revocation timestamps,
  and optional rotation linkage; the reusable refresh token itself is not stored.
  Access tokens carry the session ID and are rejected as soon as that session has no
  active refresh token, so logout invalidates access immediately without revoking other
  sessions for the admin.
- `ContactEnquiry` stores the validated public contact form fields, server creation
  timestamp, and notification outcome independently of student records. Public users
  can create enquiries but cannot list or read them; an authenticated Admin can list
  paginated enquiries and inspect normalized notification outcome/error codes.
- Enquiry class is constrained to `Playway`, `Nursery`, `LKG`, or `UKG`; notification
  state is `Pending`, `Sent`, or `Failed`. The row is created before external
  notification; provider failure never removes the enquiry.
- `photoLocator` is a private opaque storage reference, not a URL or public file path.
  Photo uploads create new student revisions. Previous photo references remain on
  their historical revisions so they can be retrieved only through authenticated,
  student-owned photo routes.

## Initial administrator seed

Set `ADMIN_INITIAL_EMAIL` and `ADMIN_INITIAL_PASSWORD` in the local environment before
running `npm run db:seed`. The seed requires a valid email and a password of at least
12 characters, hashes it with Argon2id, and does not overwrite an existing admin's
password on repeat runs. Credentials are never included in source control. Password
rotation must be performed through a deliberate administrative procedure; rerunning
the seed is not a rotation mechanism.

## Migration status

The initial migration is the first-release baseline; the following migration adds
refresh-token session IDs. Do not edit an applied migration; subsequent changes must be
additive migrations. Apply migrations only to a disposable or explicitly approved
development PostgreSQL database.
